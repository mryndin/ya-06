
# Архитектурное решение по логированию

## 1. Мотивация

В текущей архитектуре (Интернет-магазин, CRM, MES) любые сбои в цепочке обработки заказа (от загрузки 3D-модели до производства) требуют долгого ручного расследования.

**Цели внедрения:**

-   **Снижение MTTR (Mean Time To Recovery):** Возможность мгновенно видеть, на каком этапе «отвалился» заказ (например, потерялся в `Messages Queue` или API вернуло ошибку при загрузке в S3).
    
-   **Бизнес-прозрачность:** Понимание воронки заказов через логи (сколько заказов создано vs сколько передано в производство).
    

**Ключевые метрики:**

1.  **Business:** Конверсия загрузок 3D-моделей в успешные заказы.
    
2.  **Business:** Время от создания заказа до начала производства (по логам MES).
    
3.  **Technical:** Количество ошибок 5xx на API (Shop, CRM, MES).
    
4.  **Technical:** Среднее время обработки сообщения в `Messages Queue`.
    

## 2. Анализ и требования

Согласно C4-диаграмме, ключевые точки сбора логов:

-   **Shop API:** Входная точка пользователя.
    
-   **CRM API:** Точка взаимодействия с клиентами.
    
-   **MES API:** Точка производства.
    
-   **Messages Queue (RabbitMQ):** Хаб взаимодействия систем.
    

### Примеры логов (Уровень INFO):

-   **Shop API (Загрузка модели):** `{timestamp, trace_id, user_id, action: "3d_file_upload", file_hash, status: "success/failed"}`.
    
-   **CRM API (Статус заказа):** `{timestamp, trace_id, order_id, status_old, status_new, actor: "seller"}`.
    
-   **MES API (Назначение на оператора):** `{timestamp, trace_id, order_id, operator_id, action: "assign_order"}`.
    

### Уровни логирования:

-   **DEBUG:** Только для dev/staging окружений (подробные данные HTTP-запросов).
    
-   **INFO:** Жизненный цикл заказа (создание, смена статуса, загрузка файлов).
    
-   **WARN:** Задержки ответов (latency > 2s), повторные попытки (retries) записи в DB.
    
-   **ERROR/FATAL:** Недоступность баз (Shop DB, MES DB), ошибки S3, ошибки интеграции с Queue.
    

## 3. Приоритезация (Roadmap)

1.  **Очередь 1:** **Shop API** и **CRM API**. Это критические точки. Если клиент не может загрузить файл или сделать заказ, бизнес теряет деньги немедленно.
    
2.  **Очередь 2:** **MES API** и **RabbitMQ**. Нужно для понимания эффективности производства и целостности данных между сервисами.
    
3.  **Очередь 3:** Инфраструктурные логи (K8s, Postgres).
    

## 4. Предлагаемое решение

-   **Сбор:** Использовать `FluentBit` (Sidecar или DaemonSet в Kubernetes).
    
-   **Транспорт:** Логи направляются в `Loki` (в составе стека Grafana).
    
-   **Визуализация:** Dashboards в Grafana с корреляцией по `trace_id` (OpenTelemetry).
    

**Политика безопасности:**

-   **Маскирование PII:** Регулярные выражения в конфигурации FluentBit для удаления персональных данных (email, телефоны, ФИО) до отправки в Loki.
    
-   **Доступ:** Только инженеры сопровождения и Senior-разработчики через SSO/LDAP.
    

**Политика хранения:**

-   Индексы разбиты по сервисам (например, `logs.shop.api`, `logs.mes.api`).
    
-   **Retention:** 30 дней в «горячем» хранилище, далее удаление или архивация.
    

**Анализ:**

-   **Алертинг:** Настройка алертов в Grafana на "Spike" (всплеск) ошибок.
    
-   **Аномалии:** Мониторинг скорости обработки очередей RabbitMQ. Если сообщение висит в очереди > 10 минут — критический алерт.

## 5. Дополнительное задание: Выбор технологии

Для работы с логами (сравнение решений):


| Критерий                  | ELK (Elasticsearch)       | OpenSearch                | Grafana Loki              | Splunk                    |
|---------------------------|---------------------------|---------------------------|---------------------------|---------------------------|
| Лицензия                  | Elastic License (Огр.)    | Apache 2.0 (Open Source)  | AGPLv3 (Open Source)      | Проприетарная             |
| Потребление ресурсов      | Высокое (JVM, Индексы)    | Высокое (JVM, Индексы)    | Низкое (No indexing)      | Высокое                   |
| Масштабируемость          | Высокая, но сложная       | Высокая, но сложная       | Очень высокая (Cloud-native)| Экстремальная (SaaS)      |
| Скорость поиска           | Очень быстрая (Full-text) | Очень быстрая (Full-text) | Средняя (линейный поиск)  | Высокая                   |
| Интеграция с OTEL         | Нативная                  | Нативная                  | Нативная                  | Через коннекторы          |
| Стоимость владения (TCO)  | Средняя/Высокая           | Средняя                   | Низкая                    | Очень высокая             |
| Хранение данных           | Дорогое (большие индексы) | Дорогое (большие индексы) | Дешевое (S3/Object Store) | Зависит от объема данных  |
**Обоснование выбора:** Если ваша цель — быстрое внедрение и экономия ресурсов в Kubernetes, рекомендую **Grafana Loki**. Она проще всего интегрируется с уже имеющейся у вас инфраструктурой мониторинга и позволяет легко коррелировать метрики, логи и трейсы в одном окне.
